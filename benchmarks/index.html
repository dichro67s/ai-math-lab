We build benchmarks that test whether AI systems formalize mathematics faithfully, not only whether their Lean code compiles.

ShadowBench

A Lean 4 full-autoformalization benchmark of 178 postgraduate- to research-level problems across eight areas of mathematics, scored with SA-Pass.

The problem with compile rate

A model's Lean statement can compile and still be wrong: it may weaken the conclusion, drop a hypothesis, or assume what it should prove. Compile rate counts all of these as correct. Comparing against one reference formalization has the opposite flaw: it rejects correct statements written in a different but equivalent way.

SA-Pass (Semantic Alignment Pass) takes the idea of unit tests from code generation. For each problem, experts fix a small set of auxiliary Lean statements, called shadows, that together characterize the intended theorem. The shadows stay hidden on the evaluation server, and Lean grades any submission against them automatically.

How SA-Pass scores a statement

  1. Compile. The generated Lean file must compile on its own against Mathlib, with no sorry.
  2. Forward checks. Lean must prove that the statement implies every shadow. This catches weakened or partial statements.
  3. Backward check. Lean must prove that the shadows together imply the statement. This catches extra conclusions and dropped hypotheses.
  4. Score. SA-Pass is 1 only if all checks pass. SA-Passsoft gives partial credit: half for the share of forward checks passed, half for the backward check.

A real task (public split)

number-theory / L2 / nt_gen_L2_013. The system receives the statement below in LaTeX and must produce a single Lean 4 file that states and proves it.

Let \(p\) be an odd prime. Then \[\sum_{k=1}^{(p-1)/2}\frac{4^k}{k\binom{2k}{k}} \equiv 2\left((-1)^{(p-1)/2}-1\right)\pmod p.\]

What compile rate misses

In one case from the paper, a system formalizing Brahmagupta's formula for the area of a cyclic quadrilateral took the area itself as a hypothesis and replaced "cyclic" by an angle condition. The file compiles, so compile rate counts it as correct. It is really an identity about an assumed number, not a theorem about area, and SA-Pass rejects it.

What we found

  • Compilation overestimates alignment. In the paper, the best system (Claude Code with Opus 4.8 and Numina-Lean-Agent) compiles 61.8% of problems but reaches 11.2% SA-Pass. Newer systems compile over 90% and reach at most 18.5%.
  • Lean tooling helps compile more than meaning. Adding Numina-Lean-Agent raised Opus 4.8's compile rate by 41.6 points but its SA-Pass by only 8.4.
  • Direct prompting is far behind. Every closed, open and Lean-specialized model in the paper scored 0.0 SA-Pass when prompted directly.
  • SA-Pass matches expert judgment. On compile-passed outputs from six agentic configurations, SA-Pass agrees with experts on 98.8% of cases (BEq+: 80.6%; compile check: 17.8%).

How it was built

Problems come from graduate textbooks (Lee, Introduction to Smooth Manifolds; Stein–Shakarchi, Real Analysis; Cox–Little–O'Shea, Ideals, Varieties, and Algorithms; Boyd–Vandenberghe, Convex Optimization; Wunsch, Complex Variables with Applications; EGA; Proofs from THE BOOK), the Stacks Project, theorems missing from Wiedijk's 1000+ list, the "PRIMES is in P" paper and Mathlib 4. A language model drafts each problem's shadows, and for 85% of problems the first draft is already complete. Mathematicians review every set, and Lean checks that the shadows together characterize the reference statement. Building the checkers takes about ten minutes per problem on average.

What it contains

More than 1,200 Lean 4 problems. About 370 were written by the lab across ten areas, from graduate textbooks, the KMS College Mathematics Competition and 38 recent arXiv papers. The rest are miniF2F and ProofNet problems, re-checked under a current Lean and Mathlib. Lab-written problems come with reference Lean files and, for many, hidden forward and backward checkers.

Levels

  • L1: definitions and statements, no proofs.
  • L2: statements with short, direct proofs.
  • L3: clusters of definitions and lemmas leading to a main theorem.
  • L4: research-level results.
Evaluation server

LIFT@Seoul

Lean4 Inference and Formalization Test @ Seoul National University.

LIFT@Seoul is the lab's evaluation server. It sends each problem to a model or agent, compiles the returned Lean file in a network-isolated sandbox against a pinned Lean and Mathlib, and rejects files that use sorry, add axioms or change the target statement. It then runs the hidden forward and backward checkers and reports results by area and level. It is currently open to lab members and collaborators.
